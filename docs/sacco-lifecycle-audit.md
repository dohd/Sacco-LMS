# Sacco MVP lifecycle audit

Audit date: 2026-10-11. Result: **FAIL — the complete business workflow is not operational.**

## Run the integration test

```powershell
php vendor/phpunit/phpunit/phpunit tests/Feature/SaccoLifecycleAuditTest.php --colors=never
```

Requires installed Composer dependencies, PHP with PDO MySQL, and a reachable MySQL/MariaDB server using the configured connection credentials with CREATE/DROP DATABASE privileges. PHPUnit must boot in `testing`; cached production configuration must not be used. No dependency or production-code changes are included.

The test creates a random `sacco_audit_<16 hex characters>` database per test, runs the real migrations there, and wraps the lifecycle in a transaction. State deliberately survives between stages. Teardown rolls back and drops only that generated database, including after assertion failures. It never runs `migrate:fresh` on the configured application database. A forcibly terminated PHP process can leave its temporary database behind. Use a dedicated CI database server/account in automation.

Only the browser iframe middleware is disabled because it calls PHP `header()` directly. Authentication and application validation remain enabled; Laravel's normal test-mode CSRF behavior applies. No uploads or external payment calls are involved. Reference products, an accounting reference, and a staff user are fixtures; membership, share posting, approval, disbursement, and repayment use real HTTP routes. The accounting fixture is only a valid reference, not evidence of correct ledger mappings.

The lifecycle test exercises public User registration, logout/login, staff-assisted membership approval, a confirmed share purchase, direct loan approval from `submitted`, cash disbursement through submission/approval/processing, and repayment recording/confirmation. A separate contract test requires membership approval to provision a User. There is currently no explicit User–Member relationship; matching email in this test is a minimal provisioning check, not proof of account ownership.

Business-state mismatches accumulate until the end so downstream defects remain visible. Unexpected HTTP errors or missing records stop immediately. The test does not seed missing loan balances or schedules to disguise defects. Staff authentication is explicitly used after testing member login, allowing finance auditing even when login fails; this is not proof of a working member self-service portal.

## Executed results

PHP 7.4.33, PHPUnit 9.6.19, real MySQL/MariaDB migrations: **2 tests, 98 assertions, 2 failures**, approximately 9 seconds. These are failing acceptance tests, not expected-failure assertions or skips.

| Stage | Observed result |
| --- | --- |
| Registration | Public registration creates a User, but its password fails `Hash::check`; real login returns 422 and `last_login_at` stays null. Membership approval creates the Member but independently creates no User. |
| Shares | 500 units at KES 100 produce a confirmed KES 50,000 balance and available amount. Pending posting does not change the balance. |
| Approval | KES 12,000 for 12 months at 12% annual flat interest creates an approval and Loan, with KES 1,120 monthly installment and zero pre-disbursement balance. |
| Disbursement | Cash record reaches `processed` with net KES 12,000; loan `amount_disbursed`, principal and outstanding balance remain zero; no installments exist. |
| Repayment | KES 1,120 reaches `confirmed`, remains entirely unallocated, creates no allocations, reduces no balance, and changes the loan to `fully_paid`. Repeat confirmation returns 422 without changing the balance. |

Expected monetary contract for this product: principal KES 12,000 + flat interest KES 1,440 = KES 13,440 outstanding; first installment allocates KES 1,000 principal + KES 120 interest, leaving KES 11,000 principal and KES 12,320 total. Cash disbursement is represented by the loan funding state; the test does not prove an external bank transfer or credit a savings account. A separate account-credit/ledger test is required for that payment method.

An initial run through the optional loan review transition returned HTTP 500: `LoanApplicationsController::requireStatus` does not exist. The final lifecycle uses the supported direct approval path; this additional defect remains listed below.

## Fix checklist, simplest to most complex

Complexity determines the order below. Severity is independent: P0 = financial integrity/access blocker, P1 = major correctness, P2 = maintainability. Runtime findings above are distinguished from code-review findings below.

- [ ] **Small · P0 — Hash passwords exactly once.** `app/Http/Controllers/Auth/RegisterController.php::create` calls `Hash::make`, then `app/Models/User.php::setPasswordAttribute` hashes again. Choose one hashing owner and audit other password writers. Acceptance: registered credentials authenticate through `/login`, and `last_login_at`/IP update. Runtime confirmed.
- [ ] **Small · P1 — Restore the missing status guard.** `app/Http/Controllers/LoanApplications/LoanApplicationsController.php` calls undefined `requireStatus` from workflow, editing, deletion and security verification. Add a shared guard returning validation errors for invalid transitions. Acceptance: submitted-to-review works, forbidden transitions return 422, existing workflow tests execute. Runtime confirmed for review.
- [ ] **Small · P1 — Correct repayment reversal field names.** `LoanRepaymentsController::confirm` writes `principal_allocated`, `interest_allocated`, `fees_allocated`, `penalty_allocated`; `reverse` reads `*_amount` from allocation rows. Use the actual fields and mark allocations reversed with audit metadata. Acceptance: confirmation followed by reversal restores every schedule and loan component exactly. Code review; reversal not executed here.
- [ ] **Small · P2 — Return cookies through the response and align casts.** Replace direct `header()` calls in `AllowIframeFromWebsiteB` with response-managed cookie handling compatible with the installed stack. Cast User `last_login_at` and `is_active`; the current `email_verified_at` cast has no corresponding column. Acceptance: full HTTP tests run without the middleware exclusion. Code review.
- [ ] **Small/medium · P1 — Eliminate success responses from unimplemented CRUD actions.** `LoansController::show` and multiple financial `destroy` actions are empty. Implement reads; remove unsupported routes or explicitly reject operations. Preserve posted financial records through reversal rather than hard deletion. Acceptance: loan detail renders persisted state, and unsupported delete requests cannot return empty success. Code review; full CRUD/read/delete coverage is outside this five-stage test.
- [ ] **Medium · P0 — Validate disbursement identity, amount and transitions under locks.** `LoanDisbursementsController::store` independently accepts a loan and application without the ownership check present in `update`; submit/approve/process/reverse do not enforce source states. Lock the related records, cap cumulative disbursements at approved principal, reject invalid transitions, and prevent duplicate processing. Acceptance: mismatched applications, repeated processing, excess disbursement and missing IDs fail without mutation. Code review.
- [ ] **Medium · P0 — Provision and link member identity atomically.** `MembershipsController::approve` ends with an unimplemented `create member login` comment. Add a unique User–Member relation, safely link existing verified accounts or invite new users, and enforce approval transitions under lock. Do not rely on matching unverified email for ownership. Acceptance: a membership creates/links exactly one usable identity, retries do not duplicate it, and rollback leaves no partial identity. Missing provisioning runtime confirmed.
- [ ] **Medium · P0 — Enforce authorization and separate member/staff powers.** `routes/web.php` puts sensitive operations behind `auth`, and the reviewed controllers do not apply operation-specific policies. Public registration is enabled. Add ownership policies, staff permissions and approval separation as required. Acceptance: guest redirects, ordinary-member 403s for staff approval/disbursement, and cross-member access denial. Code review; this test uses a staff fixture and does not certify authorization.
- [ ] **Medium/large · P0 — Make disbursement establish the funded loan and schedule.** `LoanDisbursementsController::process` only updates the disbursement status/actor/time. Atomically set funding totals/dates, principal/interest balances and the schedule from immutable approved terms. Define deductions, installment dates, partial funding and interest rounding explicitly. Acceptance: KES 12,000 funding creates the 12 expected installments and KES 13,440 outstanding, exactly once. Missing effects runtime confirmed.
- [ ] **Medium/large · P0 — Reject repayment against unfunded or inconsistent loans.** `LoanRepaymentsController::confirm` accepts a loan with no schedules, leaves the payment unallocated and derives `fully_paid` from zero balances. Require a funded loan and consistent schedule; define explicit overpayment/unallocated-credit handling. Acceptance: no silent closure or lost allocation, pending state survives failed confirmation, component and total balances reconcile. Runtime confirmed.
- [ ] **Large · P1 — Consolidate financial application services and money arithmetic.** Allocation logic exists in both `LoanRepaymentsController` and `app/Services/LoanRepaymentAllocationService.php`, with different status expectations. Extract one tested posting/reversal implementation; use decimal-safe arithmetic or integer minor units with explicit rounding. Acceptance: penny rounding, multiple installments, fees, penalties, early payment and overpayment reconcile identically through every entry point. Code review; no concurrency/rounding certification here.
- [ ] **Large · P0 — Complete ledger posting and payment idempotency.** Product GL mappings and journal tables exist, but reviewed posting paths do not create balanced journals. Define posting rules for shares, cash/account-credit disbursement, repayments and reversal; link immutable entries to source transactions. For external methods, use durable payment references, retries and callback idempotency. Acceptance: balanced journals, no duplicate debit/credit on replay, and reconciliation with external settlement. Architectural recommendation based on reviewed paths.
- [ ] **Large · P1 — Harden schema and regression coverage.** Financial relationships commonly use bare integer columns without foreign keys, and migration ordering creates child tables before parents. Add forward migrations to reconcile existing data and enforce appropriate references/uniqueness without rewriting deployed history. Extend CI with MySQL concurrency, rollback fault injection, authorization, reversal, invalid-input and cross-member tests. Acceptance: orphan writes fail, simultaneous requests cannot overspend/duplicate postings, and each injected failure leaves no partial financial state. Code review/recommended follow-up.

The existing sidebar change and pre-existing untracked feature tests were left untouched. The audit adds tests and this report only; production defects remain unfixed and the failing test should remain a release gate until the contract is satisfied.
